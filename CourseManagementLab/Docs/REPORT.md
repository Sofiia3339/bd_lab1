# Лабораторна робота

**Тема:** система управління навчальними курсами.

**Мета:** розробити реляційну модель навчальної системи, реалізувати серверну обробку даних у PostgreSQL та доступ із C# за допомогою Repository + Unit of Work.

## Вимоги системи

Адміністратор створює, редагує, логічно видаляє та відновлює курси й уроки. Для курсу визначаються мова програмування, рівень, опис і ціна. Студент записується на курс, має навчальну оплату, проходить уроки та залишає відгук. Після завершення оплаченого курсу адміністратор видає сертифікат. Система зберігає історію зміни цін та повний журнал змін курсів.

## Модель даних

| Таблиця | Призначення |
|---|---|
| users | Облікові записи учасників демонстраційної системи |
| roles | Ролі адміністратора та студента |
| user_roles | Зв’язок користувачів із ролями M:N |
| admins | Профіль адміністратора, зв’язок із users 1:0..1 |
| customers | Профіль студента, зв’язок із users 1:0..1 |
| programming_languages | Довідник мов програмування |
| course_levels | Довідник рівнів курсів |
| courses | Каталог курсів |
| lessons | Уроки курсу, зв’язок courses → lessons 1:N |
| enrollments | Записи студентів на курси; зв’язок студентів і курсів M:N |
| lesson_progress | Виконання уроку в межах конкретного запису |
| payments | Навчальна оплата запису на курс |
| reviews | Відгук і оцінка за записом на курс |
| certificates | Сертифікат завершення навчання |
| course_price_history | Історія цін курсів |
| course_history | Журнал змін курсів із даними до й після операції |

Схема містить 16 таблиць і 28 зовнішніх ключів. Унікальні обмеження забороняють повторні email, дублювання запису студента на курс, повторну оплату, відгук або сертифікат для одного запису. Складений ключ `user_roles` забороняє повторне призначення ролі. Для активних уроків порядковий номер у межах курсу унікальний. `CHECK` обмежують ціни, оцінки та узгодженість полів видалення і завершення уроку.

Схема: `schema.drawio`; текстова модель: `schema.dbml`. Джерелом повної фізичної структури є `Database/install.sql`.

## Логічне видалення та аудит

Таблиці `courses`, `lessons`, `reviews` містять `is_deleted`, `deleted_at`, `deleted_by`. Видалення змінює ці поля без фізичного вилучення рядка. `v_catalog` повертає активні курси, а `v_course_admin` дозволяє переглядати також видалені.

У `courses`, `lessons`, `reviews`, `enrollments`, `lesson_progress` зберігаються `updated_at` і `updated_by`. Процедури отримують ID користувача та записують автора, а тригери `tr_*_touch` автоматично оновлюють час редагування. Початковий час задається значенням за замовчуванням.

Тригер `tr_courses_audit` після створення або оновлення курсу додає подію в `course_history`. Якщо ціна змінилася, додатково створюється запис у `course_price_history`. Повторне збереження тієї самої ціни не створює зайвого рядка історії цін.

| Вид | Об’єкти |
|---|---|

| Обчислювальні функції, 2 | enrollment_progress, course_rating |
| Перевірка ролі, 1 | require_admin |
| Тригерні функції, 2 | touch_updated_at, audit_course |
| Тригери, 6 | tr_courses_touch, tr_lessons_touch, tr_enrollments_touch, tr_progress_touch, tr_reviews_touch, tr_courses_audit |

Навіть без допоміжних і тригерних функцій реалізовано більше десяти об’єктів. Функції прогресу та рейтингу використовуються у View, процедури — із репозиторіїв, тригери виконуються автоматично під час запису.

Прогрес — частка виконаних активних уроків серед усіх активних уроків курсу. За відсутності уроків прогрес дорівнює нулю. Процедура завершення перевіряє, що урок належить курсу запису, курс та урок активні, запис оплачений, а виконавець — власник запису або адміністратор.

## Індекси

`ix_enrollments_customer` використовує B-tree для пошуку записів студента. `ix_courses_search` використовує GIN для стовпця `search_document` типу `tsvector`; документ формується з назви та опису. Частковий індекс охоплює активні курси. Каталог виконує пошук через `plainto_tsquery` та оператор `@@`.

Додатково створені індекс історії цін за курсом і датою та частковий унікальний індекс порядку активних уроків. План виконання можна переглянути за допомогою `EXPLAIN (ANALYZE, BUFFERS)`. Вибір індексу залежить від обсягу даних і вартості плану.

## Repository та Unit of Work

Реалізовані `ICourseRepository`, `ILessonRepository`, `IEnrollmentRepository`, `IPaymentRepository`, `IReportRepository` та відповідні класи. У репозиторіях усі запити читання звертаються до View, а зміни виконуються через `CALL`. Параметри передаються окремо від тексту SQL.

`UnitOfWork` створює репозиторії зі спільним контекстом з’єднання. Методи `Begin`, `Commit`, `Rollback` керують спільною транзакцією Npgsql. Репозиторії не відкривають власні незалежні транзакції.

`SchoolService.EnrollAndPay` виконує дві операції: створення запису та оплату. Погоджена ціна фіксується на момент запису. Якщо сума оплати неправильна, процедура викликає помилку, а Unit of Work відкочує також створений запис. Якщо обидві операції успішні, вони підтверджуються разом. Серверні процедури не виконують власний COMMIT, тому межа цієї транзакції залишається в C#.

## Перевірка

`Database/verify.sql` перевіряє структуру, оновлення аудиту, історію цін, права адміністратора, логічне видалення та відновлення, скасування запису після помилки оплати, належність уроку курсу, прогрес, умови видачі сертифіката та облік відгуків. Перевірки завершуються відкатом.

Демонстраційний вебінтерфейс дозволяє повторити ці сценарії вручну. Автентифікація за паролем і реальні платежі не входять до цієї навчальної реалізації.

## Висновок

Розроблено реляційну модель із 16 сутностей. Реалізовано логічне видалення, аудит, серверну обробку даних, індекси B-tree і GIN та доступ із C# через Repository + Unit of Work. Транзакція запису й оплати забезпечує узгоджене збереження пов’язаних даних.
